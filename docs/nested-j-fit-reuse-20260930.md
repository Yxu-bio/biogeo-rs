# 六模型批处理复用无 J 拟合

开发版：`0.1.6-dev.20260930`，Windows x86_64 MSVC。公开分析结果和逐起点诊断格式不变。

## 改动

以前六模型批处理先保存 DEC，随后 DEC+J 在内部又把 `j` 固定为 0、重新拟合一次 `d/e`。
DIVALIKE 和 BAYAREALIKE 也存在同样的重复工作。

现在批处理按 manifest 顺序寻找已成功完成的无 J 结果。仅当它收敛、自由参数是 `d/e`，
目标自由参数是 `d/e/j`，无 J 的 `j` 固定为 0，且除 `j` 外所有参数定义完全一致时，
才从经过校验的保存结果中读取 `d/e`。两次任务共享批处理的树、范围、时期等输入和优化设置。
这样允许三对标准 preset，也允许名称不同但参数表相同的模型；不会仅凭 `DEC` 等名称配对。

原始起点、两个不同 `j` 值的继承起点和用户显式提供的其他起点仍会运行。
优化器仍选择其中最好的有效结果。复用时不再做内部 `j=0` 评估，因而 `+J` 的本次
`optimization_evaluations` 不包含前一个模型已经完成的工作。`optimization-starts.tsv`
只记录实际运行的 `target` 起点，不伪造一个 `nested_j_zero` 条目。

单独运行 `+J`、无 J 模型排在后面、参数表不匹配或前一个拟合未收敛时，沿用原来的
内部 `j=0` 拟合。关闭无 J 继承起点的选项也继续生效。已保存的旧拟合不会在
`--resume` 时重新优化；要获得省时效果，需要在新目录重新运行。

## 八端点原始请求对照

使用用户保留的八端点、三区域原始六模型请求，各跑 include/exclude null。
旧 exe 为 `0.1.5-dev.20260930`，新 exe 为 `0.1.6-dev.20260930`。
两边每起点最多 200 次迭代、`max_range_size=3`，结果写在本项目
`output/nested-j-reuse-20260930/`，原始文件未改动。

| null | 模型 | 旧版似然评估 | 新版似然评估 | 省下 |
|---|---|---:|---:|---:|
| include | DEC+J | 1108 | 956 | 152 |
| include | DIVALIKE+J | 1070 | 927 | 143 |
| include | BAYAREALIKE+J | 830 | 688 | 142 |
| exclude | DEC+J | 872 | 752 | 120 |
| exclude | DIVALIKE+J | 1035 | 897 | 138 |
| exclude | BAYAREALIKE+J | 919 | 765 | 154 |

include 的六模型总评估从 3445 降为 3008，减少 437 次；exclude 从 3238 降为
2826，减少 412 次。每一项节省数正好等于前面对应无 J 模型的评估次数。
两种 null 设置共 12 个模型的最终参数文件 SHA256、lnL 位值、收敛状态均一致；
两份六模型比较表与模型平均结果也都逐字节相同。

小树单次运行约 0.4 秒，进程启动和系统波动会影响墙钟计时，因此本例只把评估次数
当作稳定的节省指标，不据此推断大型树的固定加速比例。

## 回归验证

- 端到端测试验证三对 preset 的继承起点确实使用前面保存的 `d/e`，并检查
  DEC+J 独立运行与批处理的最终参数相同，二者评估次数之差恰好是内部无 J 拟合次数。
- 测试覆盖无 J 模型排在 `+J` 后面、两张参数表初值不同、恢复运行、八端点六模型比较。
- 完整 `cargo test --workspace`：454 项通过，0 失败；2 项既有测试默认忽略。
- `cargo clippy --workspace --all-targets -- -D warnings`：通过。
- release 模式的小树、RASP 宿主与 schema 契约测试：12 项通过。
